2. summary/_repos metadata says needsLLM: 0, but 16/34 workers used LLM inference
------------------------------------------------------------------------------
data["_repos"][0]["needsLLM"] = 0

But per-worker data["workers"][i]["inference"]["provenance"] is "llm" for 16
of the 34 workers (47%), each with an attached confidence score (0.85–0.95),
matching the "(llm, confidence 0.NN)" annotations visible in the PDF's Worker
Inventory section (e.g. notify-customer, check-identity-bureau, reserve-funds,
retry-alternate-rail, submit-payment-rail, and 11 others).

This is an internal inconsistency in the JSON itself: whatever "needsLLM"
is meant to signal (e.g. "did this repo require LLM-assisted analysis,"
useful for cost/audit tracking) contradicts the ground truth already present
in the same file, one level down.

3. Inconsistent source-code redaction (minor)
------------------------------------------------------------------------------
6 of 34 workers have their job-type string literal replaced with
"***REDACTED***" inside sourceCode.code, while the other 28 show it in plain
text. The redacted ones show no discernible pattern (not tied to secrets,
PII, or any field flagged elsewhere):

  build-regulatory-dataset, classify-transactions-dmn,
  publish-ledger-posted-message, release-fund-reservation,
  manual-onboarding-review, record-supplementary-evidence

In every one of these 6 records the same literal is still present in plain
text one level up, in the "jobType" field and in
registration.symbol — so the redaction achieves nothing (the value is fully
recoverable from the same JSON object) and appears to be an unintended,
partial application of a redaction rule rather than a deliberate policy.

Net effect
------------------------------------------------------------------------------
Anyone reviewing only the polished PDF — which is the artifact meant for
stakeholders — would conclude this estate has zero secrets issues and that
LLM-assisted (i.e. lower-confidence, harder-to-audit) inference wasn't used.
Both conclusions are wrong per the tool's own raw output. Recommend filing
against the report-rendering layer in the shinro repo before this tool is
pointed at a real customer estate, since a real customer will act on the PDF,
not the JSON.
