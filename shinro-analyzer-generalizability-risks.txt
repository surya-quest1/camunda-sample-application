Shinro Code-Analyzer — Generalizability Risks
Repo: camunda-sample-application
Source: code-analysis.json (schemaVersion 1.3.0)
Noted: 2026-08-22

Question: will this analyzer work on other Camunda applications, not just this
purpose-built reference estate?

Verdict: proven on the fixture it was built to pass; most of the hard parts
of code analysis are untested, because the estate was engineered to avoid
the cases that would stress them.

------------------------------------------------------------------------------
1. Side-effect classification is a shallow rule, not real dataflow analysis
------------------------------------------------------------------------------
18/34 workers get sideEffectClass from a rule capped at confidence 0.7-0.75:
"call graph reaches no known I/O sink (http/jdbc/kafka/file)" — a fixed
keyword vocabulary matched against a one-hop call graph (e.g. Logger.info,
RegulatoryReportingService.buildDataset). Every worker here calls straight
into a thin *Service/*Client class: no interface indirection, no DI proxy,
no repository pattern, no multi-hop chain. Real codebases have exactly those
things; the sink-keyword rule will silently misclassify a money-moving call
as "read-only" the moment the I/O sits one abstraction layer deeper than
this fixture's flat structure.

------------------------------------------------------------------------------
2. The LLM-inferred half reasons from variable names, not verified behavior
------------------------------------------------------------------------------
The remaining 16/34 workers use LLM inference at confidence 0.85-0.95, but
the rationale is pattern-matching, e.g.: "applicationId serves as a natural
idempotency key... payment rails typically deduplicate by application ID" —
a guess about an external system it never queried. This guess feeds directly
into "Suggested retry policy" in the Work Item Register, i.e. real
remediation guidance. On an app with less conventionally-named variables,
this degrades with no way to detect the degradation.

------------------------------------------------------------------------------
3. jobTypeResolution is "static" for all 34 workers — 100%, no exceptions
------------------------------------------------------------------------------
Reconciliation (BPMN task type <-> worker registration) matches on literal
strings. This fixture's BPMN and workers were generated by the same script
(bpmn_builder.py), so strings line up by construction except for three
deliberately-planted mismatches. Real estates commonly build job types from
config, environment prefixes, or shared constants — the tool has never had
to resolve any of that, so it's unproven whether it can.

------------------------------------------------------------------------------
4. Language/registration coverage tested: 2 of roughly 7 official Zeebe SDKs
------------------------------------------------------------------------------
Only java/spring-zeebe (annotation style) and python/pyzeebe (decorator
style) appear. Zeebe also ships official/community clients for Go, Node.js,
.NET, and others — none of these are exercised by this estate.

------------------------------------------------------------------------------
5. Scope tested: single repo
------------------------------------------------------------------------------
_repos has exactly one entry. Real migrations usually span many
repos/services; cross-repo reconciliation and duplicate-job-type detection
are schema fields that exist (duplicateJobTypesAcrossRepos) but are
trivially empty here, since there is nothing to cross-reference.

------------------------------------------------------------------------------
6. Two schema fields are completely unexercised
------------------------------------------------------------------------------
sensitiveVariables: 0/34 workers populated.
testOracles: empty array (consistent with this repo having zero automated
tests).
There is no evidence these detectors work at all, positive or negative — the
fixture never gave them anything to find.

------------------------------------------------------------------------------
7. Secrets detection works where exercised, but severity calibration looks naive
------------------------------------------------------------------------------
Both planted defects were correctly caught. But all 16 of the remaining
findings are local dev-only demo credentials (cluster/.env Keycloak/Postgres
defaults, deploy-script tokens) flagged at the same "blocker" severity as a
real production credential. On a real customer scan full of legitimate local
.env files, this is an alert-fatigue risk, not a detection-accuracy risk.

------------------------------------------------------------------------------
Recommendation
------------------------------------------------------------------------------
This assessment validates the tool's BPMN-construct classification and
reconciliation logic (largely spec-driven, should transfer reasonably well)
and its secrets pattern-matching (works, but severity tuning is unproven).
It does not validate the tool's ability to handle deep call graphs, dynamic
job-type resolution, multi-repo estates, non-Java/Python SDKs, or real
test-suite ingestion. Before trusting this tool on a real customer estate,
build a second test fixture that deliberately includes: a multi-hop call
graph, at least one dynamically-resolved job type, a second repo, and a
third SDK language.
